# 冻结与验收 SOP（freeze-and-acceptance）

本技能规定「**凭什么说某套代码通过了验收**」。它是 `AGENTS.md` 红线 1（没有证据就不出数字）
与红线 6（历史 append-only）在**验证基础设施**这一层的可执行化。

**核心立场：被测对象没有冻结，任何验收结论都无效；验收证据不可复算，等于没有证据。**

## 1. 为什么需要它（三个真实事故）

| 事故 | 表现 | 根因 |
|---|---|---|
| 冻结失效 | 我声明冻结后脚本仍被并发编辑，验收白白作废两次 | 用「读一次、6 秒后复读未变」当冻结 —— **那是观察，不是机制** |
| 空证据假通过 | `manifest_sha256_identical: true`，实际两侧都是 `{}` | 路径推导错误导致 glob 空命中；**两边都空必然相等** |
| 失败无法定位 | 间歇失败 3/14，失败断言拿不到 | 只保存 `stdout_tail`，**失败那行被截断** |

## 2. 六步冻结（唯一允许的流程）

用 `work\tools\freeze_snapshot.py --create [--freeze-id <id>]`：

```text
1. 停止编辑，取得「冻结窗口 owner」（记录 pid）
2. 一次读取 -> source_inventory（每文件 path / bytes / sha256）
3. 立即复制到 <run>/snapshot/ 并设只读
4. 回读三方哈希：source / snapshot / manifest（manifest 另算自身 SHA256）
5. 全过程日志 + manifest 自身 SHA256 写入本 freeze 专属 run-id（append-only，不可复用）
6. 窗口内任一文件变化 => status=ABANDONED_CODE_CHANGED_IN_WINDOW 且 exit 6
   —— 放弃该 freeze_id，**不得靠人工解释继续使用**
```

- 冻结目录：`work\runs\lt2-supervisor-acceptance-<freeze_id>\`；`freeze_manifest.json` 含
  `source_inventory` / `snapshot_inventory` / `window` / `window_drift` / `status` / `criteria_hashes` /
  model sha256 / python 版本；另有 `manifest.sha256` 与 `freeze_procedure.log`。
- **一切测试从 `snapshot/` 执行**，绝不再从会被改动的 `work\tools` 执行。
  自检方法：验收执行器输出的 `layout.tools` 必须指向快照目录。
- 测试**前**与**后**各跑一次 `--verify`（源文件 vs manifest）与 `--verify-snapshot`，
  **四项均须 MATCH**。
- 需改代码时：新建 freeze_id，**从第一项测试整轮重跑**，旧 freeze 原样保留标 retired。

## 3. fail-closed 验收判据

- **空集合必须判失败**：被比对文件数为 0 时禁止输出「一致」。
  应报 `deterministic_manifest_empty => FAIL`（空比较永远不能算通过）。
- deterministic manifest 必须**真正枚举**被比对文件（规范化相对路径 + 字节数 + 完整 SHA256），
  并把完整数组写进 summary；**不得只写在 stdout**。
- 排除项只能来自**固定 allowlist 并逐文件附原因**；出现未知排除项即失败；
  full-tree 的每个差异都要能映射到该 allowlist，**不得用「整个目录都不确定」掩盖未知差异**。
- summary 必须含顶层 `different_files` / `only_left` / `only_right`（空数组 = 通过）。
- 每轮**完整** stdout/stderr 单独落盘，summary 记录日志路径、字节数、SHA256；
  **tail 只能预览，不得作为唯一证据**。结构化结果写 `test_summary.json`，不要从末行猜「合计」。
- 顶层 `try/finally` 保证异常时也写出 exception 类型、测试名与 traceback 日志哈希。

## 4. 运行期门禁 ≠ 事后审计（最容易被混淆的一条）

- **事后审计**：求解结束才回放时间线算事件 —— 运行期**没有任何中止能力**。
  把这种实现称作「实时中止 / hard stop」是**过度声称**。
- **运行期门禁**：每轮同时读 sidecar 健康 + `verdict` + `reasons` + `cancel_requested`，
  越线**当场**动作。注意「sidecar 健康但已判 hard verdict」也要动作，不能只等停更。
- 停止线阈值只登记在**一处**（`work\tools\rt_gate.py` 的 `Thresholds`），禁止在别处复制一套。
- 软线只阻止**下一**任务，不取消当前任务；硬线先正常取消，必要时才终止**已核对归属**
  （端口 owner PID + 进程启动时间 + run-id）的进程。
- **`PeakWorkingSet` 单调不减，只作审计**，不作实时信号；实时量看 `WorkingSet`。

## 5. 失败分类不得说谎

- `resource_hard_stop` **只能**由「活着的监控真实产出连续越线样本」推导；
  **不得**由「监控进程退出 / 无样本 / 任务启动失败」推导出来。
- 否则基础设施 bug 会被伪装成资源问题，并在生产里**掩盖**同类 bug。
- 触发记录必须区分 `threshold_crossed`（含越线样本、生效阈值、连续次数）与
  `no_samples_observed` / `integrity_failure`；**没有越线样本时不得称 hard stop**。
- 阈值写入记录时取**生效阈值**（演练覆盖值容易误写成默认值）。

## 6. 身份与判活（Windows 实测）

- **不能用 `OpenProcess` 判进程存活**：目标被终止后只要父进程仍持句柄，它依然成功。
  正确：`GetExitCodeProcess(h) == STILL_ACTIVE(259)`。
- **终止后不能只查一次**：`Stop-Process` 返回 rc=0 后 PID 与端口不会立刻消失，
  必须带超时轮询并留痕 `waited_s` / `timed_out`；终止后须二次确认
  （PID 消失 / 端口关闭 / 无意外新进程 / 终止命令退出码）。
- 优先用**监听端口取 PID**（`port_owner_pid`），不要只靠「最新同名进程」这类启发式；
  `run_id` 只是监督器的记录，**不是**操作系统进程身份。
- **mtime 不能判定代码漂移**，以 bytes + SHA256 为准（还原文件内容也会更新 mtime）。

## 7. 验收前后必须做的事

```text
验收前：前缀校验四项 MATCH；确认无其他求解进程占用资源
验收中：唯一、空的输出目录（禁止复用历史目录）；并发测试用唯一 namespace
验收后：后缀校验四项 MATCH；任何一轮失败**先保留现场并停止**，
        不得清理后重跑来覆盖失败证据
```

## 8. 常见踩坑清单

1. 把「观察两次没变」当冻结 —— 必须用哈希锁与窗口漂移判定。
2. 冻结窗口内仍有并发编辑 —— 先取得窗口 owner 并让编辑方明确停手。
3. summary 缺字段（只存在于 stdout）—— 报告字段必须进结构化产物。
4. 假阳性判据（如把服务未启动阶段的空值当「缺列」）—— 判据要限定到正确的阶段。
5. 用空比较冒充一致性（`sha256("{}")`）。
6. 把事后审计说成实时中止。
7. 拿旧自测给新代码背书 —— 代码一变，验收信用即失效。
8. 只为失败留 tail —— 失败断言必须能从落盘日志复现。
9. 拿「跑了很多次没复现」当竞态已修 —— 见 §9：竞态证据必须是**构造出必然触发窗口**。
10. 让"正常收尾"与"真触发"产出同名同形的记录 —— 记录名必须说明它**是什么**，不是它**像什么**
    （实测：一次 PASS 的正常收尾留下了 `hard_stop_enforce` 触发记录，演练证据当场失去判读力）。
11. **在交付目录里运行交付物自带的测试脚本** —— 它会覆盖被哈希锁定的产物，而且**原字节不可恢复**
    （实测 2026-09-15：复核方在 `work/ai-solver/step4\` 内复跑该交付物的 `smoke_step4.py`，
    把 `raw\smoke.json` 从 8436 B / `1d1701f3…` 覆盖为 8544 B / `57bca711…`，
    而报告正文引用的正是旧哈希 ⇒ 报告与磁盘当场不一致，只能靠**勘误记录**收场）。
    **要独立复跑，必须先把整个交付目录复制到 scratch 再跑**，或确认脚本支持 `--out-dir` 之类的重定向；
    复核方"想验证"不是覆盖别人产物的理由。含墙钟耗时/时间戳的自测产物本就**不可复现**，更不能重跑。
12. **复跑打包/汇总步骤会重写 `manifest.json`** —— 若此时目录内任一被跟踪文件已变
    （哪怕只是上一轮无意的覆盖），manifest 就会与报告里引用的 manifest 哈希脱钩。
    因此复跑 `assemble` 之后必须**重新做一次 manifest ↔ 磁盘逐件核对**并把差异登记在案
    （附带收益：把 `assemble` 连跑两次可以顺手证明**汇总步骤本身是确定性的**——
    实测 39/39 件逐字节相同，唯一差异来自其上游被覆盖的那个文件）。

## 9. 竞态类修复的证据标准（唯一可接受的形式）

```text
任何针对竞态的修复，证据只能是「**构造出必然触发窗口**」：
  - 用一个可控替身/定向复现器把窗口**钉死**（例：`supervise_child` 的 worker 命令取自模块级
    `SELF`，把 `SELF` 换成替身脚本；替身写完 `stage=closed`+checkpoint 后**再活 3 秒**）
    ⇒ 轮询**必然**命中窗口，修复生效与否一次跑清；
  - 禁止用「跑 N 次没复现」宣布修复（N 次无复现只能说明概率低，不能说明路径被拦）。
反向要求（同样重要）：**压制触发的守卫必须带"没有真实越线"例外**。
  实测教训：收尾守卫若只写「stage==closed 或 checkpoint 已存在 ⇒ 不 enforce」，
  一个恰好在收尾瞬间越线的**真实硬停**会被吃掉；正确形式是
  「stage==closed 或 checkpoint 已存在 **且 verdict != hard_stop** ⇒ 不 enforce」，
  即守卫的定义是「只在**没有真实越线**时才抑制触发」，而不是「收尾阶段一律不触发」。
可判读要求：正常收尾与真触发必须在产物里**一眼可分**
  （`trigger_kind` / `enforced_by`（drill_gate vs resource_gate）/ `is_drill_run` / 有无 signals 文件）。
两条实测补充（r8d → r3c 一轮真实翻车）：
  (a) **替身必须包含真实故障的全部条件，否则测试会"通过错误的理由"**。实测：第一版替身复现了
      `stage=closed`+checkpoint，但把 `sampler_pid` 写成 null ⇒ 旧代码落进"启动期"分支、从不 enforce，
      测试 12/12 全过，而真机 r3c 仍然失败（sampler 已退出的那条路径没被覆盖）。
      凡修复涉及"多轮轮询/状态持续"，替身必须**多轮**驻留（例：活 3 s，≥15 轮），
      并**证明测试灵敏度**：把同一套断言跑在**历史冻结快照**上，必须失败（旧代码上复现原缺陷）。
  (b) **抑制/守卫类修复必须"持续生效"且"有界"**：把"只记一次"写进守卫条件会让下一轮轮询
      落回旧路径（实测：记完正常收尾 7 s 后又 enforce）。正确形式是
      「守卫成立期间每轮都抑制」+「设上界（例 60 s），超过即升级处置」——
      持续抑制不封顶会让进程收尾卡死时把 supervisor 永久挂住。
```

## 10. 元数据自洽（R3）与回传即校验（R8）：验收侧条款

> 实施侧条款见 `comsol-batch-production` §9.3/§9.6。本节规定**验收时怎么判**。
> 来源：`docs/INJECTION_SOLVER_AUTOMATION_MERGED_20261008.md` §4（R3/R8 均有 run 证据）。

### 10.1 元数据与终态自洽（R3）：先落终态、再算清单

```text
· 接受条件：产物清单里每一个「状态类」文件，其哈希必须对应**终态**内容
  （如 status.txt 的内容必须已是 complete，而不是中间态 hashing_outputs）
· 命中「清单哈希 = 中间态」时：登记为**已定性的顺序缺陷** —— 既不是数据问题，也不是静默放过；
  要求重出清单并重新校验，旧清单原地保留（append-only）
· 禁止用「重跑一次覆盖掉」来消灭该缺陷：缺陷现场必须留痕
```

**为什么**：这类缺陷**不会**让任何数值变错，却会让人**无法判断**产物是否完整 ——
它属于「元数据不可信」，与「数据算错」同等致命，但**分类必须分开**
（与 §5「失败分类不得说谎」同一条纪律）。

### 10.2 回传即校验（R8）：逐文件哈希，豁免显式声明

```text
· 取回后逐文件对 output_manifest.tsv 比对哈希；「清单有、本地缺」与「哈希不符」**分别计数**
· 空集合必须判失败（沿用 §3：空比较永远不能算通过）
· 任何豁免（如已知的先算后写、已知含墙钟时间戳而不可复现的产物）必须：
  逐条列出 + 写明原因 + 落进结构化 summary；豁免清单是**固定集合**，不接受临时口头声明
· 禁止：把「漏扫」写成「无差异」；禁止用一句「其余文件均一致」概括未经逐一比对的部分
```

**实测背景**：R3 的中间态 `status.txt` 正是在这一步被发现「哈希不符」的 ——
**回传校验的价值正在于它会把上游的顺序缺陷暴露出来**；把这类差异豁免掉，
就等于把 R3 一起豁免掉，顺序缺陷会一直留在生产里。
