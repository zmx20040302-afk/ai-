## 1. 阻塞项：`commit ≥ 13500` 与 `commit ≤ 4096 硬停` 互斥

裁定 §Q3 给了两条路，两条都把 commit 当门禁，但这两个数字在**当前配置**下不可能同时满足：

### 1.1 前置门禁 `commit_available_mb ≥ 13500` 本机**从未达到**

```text
R0 v2 全程 159 个采样，commit_available_mb 最大值 = 11,294.9 MB
满足 >= 13500 的采样数                        = 0
本机理论上限 = commit limit − 空闲已提交
             = 37,055.6 − 25,296 = 11,759.6 MB        < 13,500
```

即：`13,500` 高于本机 commit 的**理论上限**，不是「偶尔达不到」，而是**结构上不可能**。
（附带：同一次运行里 `system_available_physical_mb ≥ 16384` 的采样只有 2 个，且都在 server 启动前。）

### 1.2 运行期门禁 `commit_available_mb ≤ 4096 连续 2 采样 → 硬停` **必然触发**

```text
R0 v2 运行期 commit 实测区间 = 647.3 – 1,300 MB
用真实样本回放新门禁：159 采样中 147 个 hard_stop
首次取消 = 2026-09-14T09:17:30  commit_hard_stop(747.1 <= 4096.0 x2)
（求解自 09:17:25 开始 → 约 35 秒后被取消）
```

### 1.3 结论与需要裁定的一点

**这两个数字只有在页面文件调整之后才自洽**——`13,500` 隐含假设了更大的 commit limit。
推导（依据：变更前实测 `limit 37,063 = RAM 32,190 + 页面文件 4,873`，等式在同一次读数内闭合）：

```text
页面文件 4,873 -> 12,288 MB  =>  commit limit 37,055.6 -> 44,478 MB（+7,415）
预测（假设背景提交量不变）：
  前置 commit  = 10,848.1 + 7,415 = 18,263 MB   >= 13,500  ✓
  运行期最低   =    647.3 + 7,415 =  8,062 MB   >  4,096  ✓（且 > 6,144，连预警都不会有）
```

**所以页面文件调整落地后，我不需要重新裁定即可继续。**

**但需要你裁定的是**：若用户的页面文件变更最终未执行（或重启后 `commit limit` 仍是 ≈37,000 MB），
§Q3 的「有人值守回退路线」按原文**不可行**（它的启动门禁 `13,500` 高于本机上限）。请二选一：

- **(a)** 撤回该回退路线，声明「页面文件不调大 → 本机不具备执行 LT2 的条件」；
- **(b)** 给回退路线一个新的 commit 前置门禁值**并说明其推导依据**——我不自造这个数字。
  （可用的实测锚点：本机上限 11,759.6 MB；R0 v2 运行期最低 647.3 MB。）
