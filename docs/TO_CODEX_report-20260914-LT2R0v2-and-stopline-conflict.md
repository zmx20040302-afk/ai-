## 2. 我自己的缺陷（主动披露，属方法学错误）

### 2.1 D1：`pass_conditions` 漏掉 commit 项 → 结论静默略过一条已声明的硬线

`lt2r0_v2.py` 里声明了 `SOFT_COMMIT, HARD_COMMIT = 4096, 1024`，并据此生成了 235 个 `hard_stop_commit` 事件；
但第 324 行起的 `pass_conditions` **只有 7 条，没有 commit 这一条**：

```
frequency_rows_7, failed_frequency_points_0, drive_voltage_mismatch_0,
monitoring_ok, peak_ws_lt_12288, min_avail_ge_4096, server_cleanup_ok
```

结果是：脚本输出 `R0_v2_status = PASS`，而同一份 JSON 里记着 91% 的采样穿越了硬线。
**这两件事不能同时成立。** 我撤回「无条件 PASS」，改判 `PASS_CONDITIONAL`。
（`peak_ws_lt_12288` 与 `min_avail_ge_4096` 两个门禁本身是通过的，问题只在 commit 被漏掉。）

### 2.2 D2：停止线是「事后审计」，运行期没有任何中止能力

`lt2r0_v2.py` 第 278 行之后才读回时间线并计算事件——即停止线判定发生在**求解全部结束之后**。
运行期不存在任何 kill 路径。因此计划文档里「hard stop / 停止线」的措辞是**误导性的**：
它描述的是事后审计，不是保护机制。**15 小时无人值守的 LT2 若照此运行，等于没有真实保护。**

### 2.3 D3：事件列表被截断，量级被藏住

第 321 行 `"stop_line_events": events[:40]`，而 `stop_line_event_count = 235`。
报告里看到 40 条、实际 235 条。截断本身可以接受，但必须在报告里显式写明「仅列前 40 条、共 235 条」——上一版没写。

## 3A. commit 近零余量的机制（补充实测）——它是算术必然，不是 COMSOL 异常

R0 v2 报告 commit 余量仅 647.3 MB，看着像异常。补测本机内存/页面文件后，机制**已定量闭合**：

| 实测项 | 值 |
|---|---|
| 物理内存 | 32,189 MB |
| 页面文件（`C:\pagefile.sys`，**系统自动管理**） | 已分配 **4,873 MB**；当前使用 833 MB；峰值使用 915 MB |
| **系统 commit limit** | 38,863,409,152 B = **37,055.6 MB**（≈ RAM 32,189 + 页面文件分配 4,873） |
| 空闲时 Committed Bytes | 26,524,889,088 B = **25,296 MB**（另一时刻 25,400 MB，随应用波动） |
| 空闲时各进程 PrivateBytes 合计 | 17,640 MB（余下为内核/分页池等，`Pool Paged Bytes` 1,578 MB） |
| 空闲时可用物理内存 | 16,948 MB |

**闭合验算**：

```text
空闲 commit                 25,296 MB
+ COMSOL 峰值增量（实测 WS） 11,236 MB
= 预期提交                  36,532 MB
commit limit                37,056 MB
→ 预期余量                    524 MB
实测余量最低                  647 MB     （差 123 MB，< 25%，同量级）
```

反过来算增量：运行期提交峰值 = 37,055.6 − 647.3 = 36,408 MB，减去空闲 25,296 MB =
**COMSOL 增量 11,112 MB**，与实测 Peak WS 11,236 MB 相差 **1.1%**。

**结论**：本机空闲时可供 COMSOL 的 commit 余量约 **11.1 GB**，而 COMSOL 需要约 **11.2 GB**——
需求与余量几乎相等，差的约 100 MB 靠页面文件在运行中被自动扩张兜住。这解释了：

1. 为什么 commit 在 solve 开始 5 s 内从 7,532 掉到 745 MB（COMSOL 一次性抬升提交量）；
2. 为什么它全程贴地却仍然成功（贴地是常态，不是故障前兆）；
3. 为什么这是**结构性**的：commit limit 只比 RAM 高 4.9 GB，因为**页面文件只分配了 4.9 GB**。

### 处置选项（按性价比排序，均需用户同意，我不擅自改系统配置）

| 选项 | 做法 | 效果 | 代价 |
|---|---|---|---|
| **A. 调大页面文件** | 关掉自动管理，显式设初始≈12 GB | commit limit 抬到 ≈44 GB，运行期余量从 0.65 GB 升到 **≈8 GB 量级** | 占磁盘；可能要重启；**属系统级改动，须用户拍板** |
| B. 运行前关掉空闲重负载应用 | 关 Chrome/Excel/ChatGPT/LZTray 等 | 回收若干 GB 提交量（空闲进程合计 17.6 GB，可回收部分） | 影响用户使用 |
| C. 什么都不改 | 维持现状 | 实测能跑通（R0 v2 已验证 504 点级单点） | 余量 ~0.65 GB，任何额外进程都可能触发失败 |

→ **我改变了上一版立场**：原先我建议「把 commit 降级为监视项」。补测后更准确的说法是：
commit 近零**不是本机的正常上限，而是页面文件配置过小的直接结果**，且有廉价修法（选项 A）。
若采纳 A，则 commit **应当保留为门禁**——因为有了真实余量之后，它才能起到「检出真实泄漏」的作用；
若无余量就把它设为门禁，只会得到一个必然触发、因而毫无信息量的红灯。

## 4. 批大小与门禁建议（附证据）

1. **禁止双 server 并行**（与既有限制一致）。物理内存 32,189 MB，单 server 峰值 11,236 MB，
   两个 server 峰值约 22.5 GB，再叠加系统与执行开销即触顶。
2. **批大小 = 4 组合 / 批，单 server 串行，每批独立 server 生命周期**（取后续指令的下界）。
   依据：跨求解不累积（1.1 节，+0.62%），且 R0 用的已是批次2 网格规模上界，故 4 组合的内层包络不超过实测值。
3. **commit 的处置见第 3A 节（本版已修正立场）**。要点：commit 余量近零是**页面文件只分配 4.9 GB**
   的直接算术结果，不是 COMSOL 异常，也不是本机的正常能力上限；
   首选处置是选项 A（调大页面文件，需用户同意），而不是把 commit 从门禁里删掉。
   我**不**建议做「压到失败」的探针测试：它会占用算力、有把机器拖到不可用的风险，
   而且在机制已经定量闭合的情况下不会产生新信息。
4. 若最终仍保留 commit 门禁（无论页面文件是否调整），它都**必须能实时中止**（与 D2 一起修），
   否则门禁只是事后记录，对 15 h 无人值守运行零保护。
