## 一、已经实现、而且真机验证过的

| # | 能力 | 实际情况 |
|---|---|---|
| 1 | **改参数 → 重算 → 出结果，全自动** | 给一组参数，自动重建几何 → 重划网格 → 跑 7 个频点 → 取 7 行结果 → 自检 → 存档 → 关 COMSOL。**全程不用人盯** |
| 2 | **一组约 13–14 分钟** | 求解实测 744–765 秒（12.4–12.7 分钟），加装模型/划网格/存档/清理 |
| 3 | **每组参数用独立的 COMSOL 实例** | 组合之间互不污染（绕开"一个进程只能连一个 COMSOL"的限制，已真机证实） |
| 4 | **求解后的完整交付** | 7 行结果 + 几何/选择集自检 + 原子存档 + 清理 + 确认端口释放（**首次完整跑通在 r3d**） |
| 5 | **内存实时监控 + 自动刹车** | 每 5 秒记录；越线就终止**自己那个** COMSOL。真机演练验证过：**你桌面开着的 COMSOL 界面全程没被碰** |
| 6 | **该跑不该跑，它自己会拒** | 内存不够 / 端口被占 / 代码被改过 / **有 COMSOL 家族进程在跑** → 拒绝启动，**不会偷偷降标准硬跑** |
| 7 | **版本防伪（冻结 + 哈希锁）** | 每次运行都被冻结并逐字节校验，跑完再验一次；改动即作废。**靠它抓出多次"偷偷改了代码"和快照被污染** |
| 8 | **失败可复现** | 之前"跑 7 次坏 1 次"的崩溃，被**变成必然复现**、找到根因（Windows 文件替换冲突 + 无重试），修好后同一压力下 7/80 → 0/80 |
| 9 | **"记录名必须等于语义"的守卫** | 计数器、布尔、键名一旦语义不符就报错。**今天靠它避免整个 504 点批次全部作废** |
| 10 | **已有数据的分析** | 质检、排名、Pareto（4 个指标对）、频响指标（带宽/平坦度）、新旧驱动归一化对照 |
| 11 | **平台侧** | 数据契约可机器校验（8 schema + 8 合法/17 非法样例）；MCP 加了路径校验；`pytest` 恢复（240 通过） |
| 12 | **MEMS 模式已丰富** | 新增技能 `freeze-and-acceptance`、`comsol-batch-production`（**live 生效**）；用户级预设校验通过，**需重启 DSH + 新建会话**才装载 |

## 三、存在的问题（按要紧程度）

### 1. 今天刚抓到的"会作废整批"的缺陷 —— **已修，待验证**

```
症状：r3f（一次正常的资源确认）算得完全正常（rows=7、无错误），却被判失败
根因：一个"计数"字段（值 0，表示"没有任何越线样本"——这是好结果）
      被放进了"只允许布尔"的容器里 ⇒ "全部为真"判定把它当 False ⇒ 整个组合失败
后果：正常路径每次都会带这个计数 ⇒ 【504 点会每一个组合都被判失败】
      ⇒ 跑满 15–17 小时，零个可用结果
现状：已修（计数移出布尔容器 + 加结构性守卫 + 系统性扫了 745 个存档确认只有这一族）
      已冻结待验证 —— 下一步跑 r3g 确认
```

**这条正好证明了两件事**：① 演练和资源终止那两次刚好都能掩盖它，只有"干净的正常运行"能暴露；② 我压着不放行批量生产是对的。

### 2. 验收套件里有个**间歇失败**（T14）

同一版代码跑两次，一次 81/82、一次 82/82，失败项是 T14。已有三条证据说明**不是**本次改动引入（写在改动范围之外、同版本内时有时无、该文件只出现在特定目录）。**待修**（验收工具自己间歇失败，等于证据不可信）。

### 3. 三个"名字与语义不符"的记录（同一族，已裁定要改）

- `termination_trigger.json`：一个**根本没发生终止**的正常运行里也存在这个名字的文件，读证据的人会误读；
- `blocked_reason`：把"什么失败了"和"为什么不重跑"粘在一句里，读起来像"因正常完成而失败"；
- `currentdrive_fmax45_v1.mph`：**文件名说是"电流驱动/fmax45"，但哈希与原始模型完全相同**——**名字是假的**（已有哈希证据）。

### 4. 其它已知、已登记但不阻塞的问题

- `read_json_safe` 读失败时返回空对象 ⇒ 最坏"把健康任务误判为启动失败并重跑一次"（**稳健性缺陷，非正确性缺陷**）；
- 硬停分类依赖**原因文本匹配**（若改文案会退化为"未分类"，虽仍 fail-closed 但丢掉可重跑机会）；
- 极端压力测试下仍有 **2.4%** 写失败（4 写 4 读、约 2500 倍生产读频率，**非生产工况**）；
- 两个只差一个连字符的模型文件（`...2-new.mph` 与 `...2new.mph`）**是两个不同文件**，易混；8.3 GB 那个还带 `.lock`（可能被 GUI 打开）；
- 子代理可能在未明确禁止时做**探索性动作**（昨天出现来源未定的 COMSOL 探针）；我已把约束收紧为"任何拉起 COMSOL 家族进程的动作都要先报备"。

### 5. 我自己犯过、已记录在案的错误（不影响结论，但要留痕）

- 把两个只差一连字符的模型文件混为一谈，而且**拿记忆里的哈希当证据**；
- 做了 diff **却没读内容**就恢复代码，把子代理正在做的修复覆盖掉（**靠我先保全了副本才没丢**）；
- 多次**字段/列名猜错**导致"以为数据缺失"（`is_pareto_front`、`usable`、`f_peak_*`、`termination_rec` 路径等）。
