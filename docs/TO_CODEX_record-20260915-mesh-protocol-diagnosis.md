## 0. 结论（实测，非推断）

> **机制 = 两份 `.mph` 文件的网格特征「实体选择集」不同 ⇒ 网格不同 ⇒ 同参数下解不同。求解协议（batch vs study）完全无关。**
> `fmax`/`hmax` 口径变更假设**不必要**：文件里那份 live 网格（151,805 单元）就是**批处理最后一个案例 `(x_scale=0.8, N_w_te1=18)` 自己的网格**。

三条独立证据：

| # | 证据 | 读数 |
|---|---|---|
| 1 | **协议无关** | 同一文件（range005）、同一 (0.6,4)：`batch p1` 单点协议 ⇒ `Ptot@15MHz = 7.186469222627108e-06`；0604 协议（停用 param + 显式 `param.set` + `std1.run`）⇒ **7.186469222627108e-06**。**7 个频点逐位相同**（T2 rows == T3 rows 判定为 True） |
| 2 | **网格是决定因素** | 同一协议（0604 式）换文件即变：base 文件网格（136,250 单元）⇒ 7.031303720021646e-06（相对差 **2.16%**）；range005 文件网格（90,438 单元）⇒ 7.186469222627108e-06（相对差 **0.076%**）。已存解 = 7.181004666528165e-06 |
| 3 | **两文件网格差异的实体证据** | 同参数下几何**逐位相同**（拓扑 83/217/152/16、外电极面积与 Ptot 控制面面积相对差 **0.0**、Ptot 包围盒相同），但网格特征的**选择集**不同（§5 表） |

⇒ 我方 0604/72-grid 两轮的残差（0.16%–2.14%）**不是**协议噪声、不是 `fmax` 口径、不是状态累积，
而是**"用 base 文件的网格描述 range005 的已存解"**这一口径错配。换成与已存解**同一个文件**后残差降到 **0.076%**。

**对 S1/S2 的含义**：这个 0.16%–2.14% **可以且应当**从误差预算里剔除（它是口径错配，不是模型误差）；
替换为同文件口径后剩余 **0.076%**，远低于 S1 的 2% 与 S2 的 3%。**但剩余 0.076% 本轮未能归零**，如实登记（§8）。

## 10. 证据等级、不确定度、没做到的地方

**证据等级**
- 「151,805 = `(0.8,18)` 这一例的网格」：**强**（162 行指纹表唯一命中，且**单元数与顶点数两个指纹同时相等**）。
- 「协议无关」：**强**（同文件两种协议 7 个频点逐位相同）。
- 「网格（选择集）是残差主因」：**强**（同协议换文件：2.16% → 0.076%；且几何逐位相同、设置相同、选择集不同）。
- 「`fmax` 假设不必要」：**强**（§4 命中即可替代；且 M0-d 四档无一命中，最大 149,119 < 151,805）。
- 「逐 case 网格未保留」：**中**（枚举 + 两处 API 不可用；不排除更低层 API 有别的通路，本轮未找到）。

**不确定度 / 没做到**
1. **剩余 0.076% 未归零**（§8），机制未完全钉死；归零需逐案例网格取证（设计改动，本轮不做）。
2. **与既有口径的冲突未解决**：运行时显示两文件网格**选择集不同**，与"`.m` 逐行相同"不一致（§6 注）。
   解决它只需离线比对两份 `.m` 的 `selection` 行——本轮未获授权读桌面 `.m`。
3. **T2 的协议偏离**：为防 162 例嵌套扫描，同时把 `std1.param` 收敛到单点（§7.2），
   严格意义上 T2 不是"只动 batch"的原版协议；T3 的存在使该偏离不影响结论（两协议给出的值逐位相同）。
4. **T1 未拿到逐 case 网格**：`SolverSequence.getMesh()` 需要 `(String)` / `(String,int)` 参数，
   `getMeshCaseTags()` 客户端 API 无；**没有**用当前网格冒充任何案例的网格。
5. 会话 A 的一处读数错误已自查更正（§2 注），旧产物未修改、以本报告为准。
6. `batch.run()` 会清空内存中既有解（§7.1 副作用）；**切勿**在还需要文件里已存解的会话里跑 batch（除非先 save）。
7. 两文件网格**为何**选择集不同（人工改动？不同建模会话？）本轮**未查**——只证明了"不同"，未证明"怎么变成不同的"。
