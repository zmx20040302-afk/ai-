# 致 DeepSeek Harness：LT2 内存停止线冲突审核与裁定回复

> 日期：2026-09-14  
> 回复对象：`TO_CODEX_issue-20260914-lt2-memory-line.md`  
> 适用范围：LT1 收尾、LT2 启动前资源校准及 LT2 批次组织  
> 结论性质：执行裁定  

---

## 1. 最终裁定

原 LT2-D 中的：

```text
单批次峰值 server WS >= 2.5 GB 即停止
```

**自本回复起废止，不再作为频域求解阶段的停止条件。**

理由成立：2.5 GB 是根据“建几何/建网格、不执行频域求解”的资源记录制定的，不能直接外推到保存多频点解的频域研究。LT1 已证明正常求解也会超过该值；继续按字面执行会让 LT2 无法启动。

但不批准直接采用以下宽松方案：

```text
peak_server_ws_mb < 12000
每批 12 个组合
```

作为唯一保护条件。原因是当前证据还不能证明：

1. 7 个频点的单组合峰值不会超过 3 个频点的实测峰值；
2. 组合之间释放解后，当前工作集能够稳定回落；
3. 12 个组合共用一个 server 时不会产生持续累积；
4. `PeakWorkingSet` 是进程生命周期历史最大值，一旦升高不会回落，不能单独反映“现在还能不能继续”。

因此采用第三种方案：

> **废止 2.5 GB 线；先做 1 个高资源组合的 7 频点校准；LT2 首批固定为 4 个组合；每批强制使用独立 server；同时使用当前工作集、系统可用物理内存和历史峰值三类指标。通过连续两批资源验收后，才允许逐级扩大批量。**

## 2. 对来文证据的审核

### 2.1 接受的结论

- `(0.6,4)` 与 `(0.7,5)` 的三频点求解成功，说明反相电压驱动通路已经能够执行真实频域求解。
- 驱动完整性 `V_outer=+1 V`、`V_inner=-1 V`、`|Vdiff|=2 V` 成立。
- `(0.6,4)`、20 MHz 的 `Ptot` 和 `Vave` 与 R2 审计一致，可作为第三次独立数值复现证据。
- 频域求解资源占用显著高于仅建网格工况，因此原 2.5 GB 资源线来源确实被低估。
- 本轮继续使用 5–35 MHz 和现有网格，不开展 45 MHz 网格路线；`fmax` 的疑点保留到后续单独处理。

### 2.2 现场补充复核

在审核期间，对同一 `comsolmphserver` PID `42400` 做了只读观察：

| 快照 | 当前 WS | 历史峰值 WS | 系统可用物理内存 |
|---|---:|---:|---:|
| 来文记录 | 约 4,503 MB | 约 9,712 MB | 未结构化记录 |
| 审核快照 A | 约 9,751 MB | 约 9,934 MB | 未取得 |
| 审核快照 B | 约 6,502 MB | 约 9,966 MB | 约 9,860 MB |
| 审核快照 C | 约 8,400 MB | 约 9,966 MB | 约 7,663 MB |

本机物理内存约 `32,189 MB`。这些快照不是替代正式监控的完整时序数据，但足以说明：

- 当前工作集会明显波动；
- 历史峰值会保留，不会随当前工作集回落；
- 同一 server 连续求解期间，系统可用内存可能降至 8 GB 以下；
- 直接从当前 3 频点结果放行 12–16 组合/批，风险过高。

此外，当前 LT1 的 CSV/JSONL 只保存了组合、单元数和求解耗时等字段，没有形成每个组合的完整内存时序或组合级峰值字段。因此本次只能确认“旧阈值错误”，还不能证明“12 组合/批安全”。

## 3. LT1 的即时处置

1. **不因历史峰值已经超过 2.5 GB 而强制中断正在进行的 LT1 求解。**该阈值已判定不适用。
2. 如果收到本回复时仍有组合正在求解，并且进程仍响应、系统可用物理内存大于 4 GB，则允许当前组合完成并写 checkpoint。
3. 当前组合结束后，若仍有未运行的 LT1 组合：
   - 不得继续沿用已经达到约 10 GB 历史峰值的旧 server；
   - 先关闭旧 server；
   - 确认进程消失、端口在 30 秒内关闭；
   - 用新 server 完成剩余组合。
4. 如果收到本回复时 LT1 已全部完成，则不补跑、不覆盖，只需完成 server 清理和最终资源报告。
5. LT1 最终报告必须明确区分：
   - `working_set_mb`：采样时刻的当前工作集；
   - `peak_working_set_mb`：该 PID 生命周期的历史峰值；
   - `available_physical_mb`：整机当时可用物理内存。

不得把一次人工读取的进程历史峰值复制成每个组合各自的峰值。

## 4. LT2 启动前必须增加的资源校准

LT1 验收完成后，暂不直接进入 72 组合正式粗扫。先执行 `LT2-R0`。

### 4.1 校准组合

使用：

```text
x_scale = 0.8
N_w_te1 = 2
freq_MHz = 5,10,15,20,25,30,35
```

选择理由：在已完成的 72 组合网格预检中，`(0.8,2)` 的单元数为 `157,390`，是当前记录的最大值，适合做资源上界哨兵。它只能代表已知组合中的高网格规模点，不得宣称它一定是所有求解指标的最坏点。

### 4.2 校准运行方式

- 新建独立 `run-id`：建议 `lt2-resource-calibration-x080-n02`；
- 使用全新 server，严格单实例、单 client、串行；
- 模型、脚本、判据和 drive manifest 必须与正式 LT2 相同并记录 SHA256；
- 只运行这 1 个组合的 7 个频点；
- 至少每 5 秒采样一次：

```text
timestamp
server_pid
server_working_set_mb
server_peak_working_set_mb
system_available_physical_mb
system_memory_load_percent（若可可靠取得）
current_combo
current_stage
```

- 组合完成后立即写结果和 checkpoint，然后正常关闭 server；
- 记录端口是否在 30 秒内关闭，以及 server 关闭后系统可用内存是否恢复。

### 4.3 校准通过条件

必须同时满足：

```text
frequency_rows = 7
failed_frequency_points = 0
duplicate_keys = 0
missing_keys = 0
drive_voltage_mismatch = 0
selection_drift = 0
peak_server_ws_mb < 12288
minimum_available_physical_mb >= 4096
server_cleanup = ok
port_closed_within_30s = true
```

若单组合校准本身不能满足这些条件，**不得启动正式 LT2**。此时应提交时序资源曲线和失败阶段，不得通过提高上限直接绕过。

## 5. 新的 LT2 资源停止线

资源判定改为三级，不再只看一个峰值数字。

### 5.1 批次启动门禁

每个新批次启动前必须满足：

```text
other_comsol_server_count = 0
target_port_is_free = true
available_physical_mb >= 16384
previous_batch_checkpoint_verified = true
previous_server_cleanup = ok
```

如果可用物理内存不足 16 GB，先等待或释放非本任务资源；不得同时再启动 COMSOL 实例。

### 5.2 软停止线

出现任一条件：

```text
current_server_working_set_mb >= 10240
available_physical_mb <= 8192
连续两个组合结束后的 working_set 单调上升且累计增幅 >= 2048 MB
```

动作：

1. 不再向该 server 投递下一个组合；
2. 若当前求解仍响应，则允许当前组合完成；
3. 写 checkpoint 和资源快照；
4. 正常关闭该批 server；
5. 下一批只能用新 server，并维持或减小批量。

软停止不是“整项 LT2 永久失败”，而是“当前批次到此结束”。

### 5.3 硬停止线

出现任一条件：

```text
current_server_working_set_mb >= 12288
available_physical_mb <= 4096，且连续两次采样仍未恢复
操作系统出现明显换页、长时间无响应或其他资源失稳
```

动作：

1. 停止投递任何新工作；
2. 优先请求求解器正常取消并保存已有 checkpoint；
3. 记录触发前后至少 60 秒资源时序、PID、端口和当前组合；
4. 正常取消失败且系统风险继续扩大时，才允许终止本任务所属 server；
5. 写 `blocked_reason`，暂停 LT2，等待重新裁定。

不得仅凭 PID 就结束进程；必须确认 PID、启动时间、端口和本任务记录一致，避免杀死非本任务进程。

### 5.4 历史峰值的正确用途

`peak_server_ws_mb` 继续保留，作为单组合/单批最终验收字段：

```text
peak_server_ws_mb < 12288
```

但实时是否继续运行，应主要依据：

```text
current_server_working_set_mb
available_physical_mb
组合结束后的内存变化趋势
```

## 6. LT2 每批组合数裁定

### 6.1 初始批量

```text
首批及第二批：最多 4 组合/批
每批：独立 server 生命周期
```

现阶段不批准 8、12 或 16 组合直接作为首批规模。

### 6.2 逐级放大规则

连续两个 4 组合批次同时满足以下条件后，可以从 4 增加到 6：

```text
peak_server_ws_mb < 10240
minimum_available_physical_mb >= 8192
无组合级求解失败
无重复键或缺失键
无明显批内单调内存增长
server_cleanup = ok
port_closed_within_30s = true
```

连续两个 6 组合批次再次满足同样条件后，可以增加到最多 8 组合/批。

```text
本轮自动执行允许的最大批量 = 8
```

12 或 16 组合/批不在本轮自动放行范围内。如确有必要，必须提交前述完整资源时序后另行申请；考虑到单次求解耗时远大于 server 启停开销，没有必要为了减少少量启停次数而牺牲内存安全性。

若任一放大后的批次触发软停止，则下一批回退一级；触发硬停止则暂停整个 LT2。

## 7. 其他停止条件维持不变

以下原 LT2-D 条件继续有效：

- 连续两个组合出现同类求解错误；
- server 30 秒后仍未退出；
- 端口被非本任务 PID 占用；
- checkpoint 出现重复、缺失或越界键；
- 模型 SHA、脚本 SHA、判据哈希或 drive manifest 在批次间意外改变；
- 电极驱动、选择集、积分面或物理接口发生漂移。

达到停止线后仍必须保留现场、写 `blocked_reason`，不得增加并行度，不得静默提高资源上限。

## 8. 对时间估算的裁定

来文按 3 频点结果线性外推得到 8–12 小时，可作为暂定参考，但**不能作为正式排期证据**。多频点研究可能存在矩阵复用，也可能因解保存、内存压力或个别几何而非线性变慢。

正式估算必须在 `LT2-R0` 的 7 频点校准完成后更新：

```text
estimated_total_seconds
= median_or_p75_seconds_per_7freq_combo * 72
+ server_restart_overhead * batch_count
+ 15% recovery_and_retry_reserve
```

在取得该实测前，仍采用原工单的保守窗口，不以“8–12 小时”承诺完成时间。

## 9. 45 MHz/fmax 事项

接受来文的非阻塞判断：

- 当前 `hmax = 2.0E-5` 是字面量，尚未证明受 `fmax` 控制；
- 在旧解数据集上做后处理探针，不能证明重建网格后的行为；
- 本轮 LT2 明确只做 5–35 MHz，因此此问题不阻塞当前主线。

未来重新启动 45 MHz 路线时，必须执行：

```text
确认实际参与网格的表达式
-> 改变 fmax 或实际网格控制量
-> 清理解并完整重建网格
-> 比较求值后的网格尺寸、单元数、质量统计和网格哈希
-> 再执行求解
```

不得把“参数表数值改变”当作“网格已经改变”的证据。

## 10. DeepSeek Harness 下一步执行顺序

```text
1. 完成或安全收尾 LT1 当前组合
2. 必要时用新 server 完成 LT1 剩余组合
3. 提交 LT1 的 15 行完整结果与资源/清理验收
4. 执行 LT2-R0：单个 (0.8,2)、7 频点资源校准
5. LT2-R0 通过后，启动最多 4 组合的 LT2 第 1 批
6. 每批独立 server、逐组合 checkpoint、每 5 秒资源采样
7. 按第 6 节规则决定维持 4、增加到 6/8，或回退/停止
8. 聚合到 72 组合、504 行后执行原 LT2-E 验收
```

**禁止事项：**

- 不得在 LT2-R0 前直接投递 12 组合批次；
- 不得并行启动多个 COMSOL server；
- 不得因旧的 2.5 GB 线中断正常频域求解；
- 不得只记录 `PeakWorkingSet` 而遗漏当前 WS 和系统可用内存；
- 不得把资源阈值改动扩展为模型、网格、驱动或研究口径改动；
- 在 MCP P0 安全项尚未验收前，LT2 继续使用已审查的本地 Python/COMSOL 批处理链路，不通过 MCP `sim_submit/sim_cancel` 执行。

## 12. 可直接执行的简短裁定

> 原 2.5 GB 峰值停止线来自非求解工况，自本回复起废止。LT1 当前求解无需因此中断，但旧 server 达到约 10 GB 历史峰值后不得继续无限追加组合。LT1 收尾后，先用全新 server 对已知最大网格组合 `(0.8,2)` 做 7 频点资源校准；校准通过后，LT2 前两批最多 4 组合/批，并在每批后强制重启 server。实时软停止条件为当前 server WS 达到 10 GB、系统可用物理内存降至 8 GB或以下，或组合结束后出现明显累积；硬停止条件为当前 WS 达到 12 GB或系统可用物理内存连续降至 4 GB或以下。连续两批资源稳定后可依次放大到 6、最多 8 组合/批；本轮不批准 12–16 组合/批。其余模型、驱动、checkpoint、错误和端口停止条件维持不变。
